## 1. Hugging Face models and datasets with no project reference
- Measured: `~\.cache\huggingface` 184.19 GB (hub 152.35 GB, datasets 31.82 GB). Largest repos: `datasets--huggan--wikiart`
  31.4 GB (last write 2026-04-25), `stable-diffusion-xl-base-1.0` 19.9 GB, `sdxl-turbo` 11.3 GB, `stable-audio-open-1.0` 9.5 GB,
  `moondream2` 8.0 GB, `IP-Adapter` 6.6 GB, `musicgen-melody` 5.8 GB. Several (`nllb-200`, `wmt22-comet-da`, `m2m100`) were written
  2026-10-02 and are very likely the excluded translation project's: BELIEVED from names, not checked (not touched).
- Feature: a "model cache" detector in the review screen. For each repo it shows size, last access/write, and which of the user's projects mention the
  repo id (text search of `*.py`, `*.toml`, `*.yaml`, `*.json`, `*.md`, `*.ipynb` under the configured project roots).
- Safety rule that would make it provable: delete only when (a) no project tree under the roots mentions the repo id, AND (b) no excluded project
  could be using it. (b) is the problem: the app is forbidden to read excluded trees, so it cannot prove (b). Honest consequence: the feature may
  only offer repos that a NON-excluded project demonstrably downloaded and no longer references, or repos the user explicitly marks; never an
  automatic tier. Restoring is a redownload (`huggingface-cli download`), so the cost of a wrong delete is bandwidth, not data.
- Effort L (reference scanner, notebook parsing, per-repo revision handling, never touching `blobs/` partially).

## 2. Docker
- Measured with read-only `docker system df` (2026-10-07): images 16 total / 3 active, 29.31 GB, **20.55 GB reclaimable**; build cache 79 entries
  25.88 GB (**4.23 GB** reclaimable by a plain prune; more with `builder prune -a`); 2 volumes (1 dangling, 48 MB); 4 containers (3 running now,
  started by other sessions: `tiq-sk`, `z8-pg`). `docker_data.vhdx` = 50.60 GB: **+34.5 GB since the 2026-10-02 compaction**; the 10-05 evening drop of
  ~20 GB is BELIEVED to be this growth (not proven; no timestamps of growth exist).
- Unused images seen (names only): `playwright:v1.63.0` 3.33 GB and `v1.62.1` 3.30 GB, `nss-forecaster:local` 1.02 GB, `review-iq-ci-smoke` x2 0.76 GB,
  `postgres` 15/16/17, `mlflow:v2.22.0`, `python:3.11-slim`, `shelfsense-m5-dagster`. `intent-router:v1` (5.82 GB) belongs to an excluded project: never offered.
- Feature: a Docker section in the review screen using the Docker CLI (`docker system df -v`, `docker images`, `docker ps -a`), plus a guided "Compact
  Docker's disk" step that prints exact admin instructions (the app cannot elevate).
- Safety rules: image = no container (running or stopped) uses it, not referenced by a compose file in a non-excluded project, created more than 14 days ago,
  and neither its repository name nor its labels match an excluded project name; build cache = entries unused for 7+ days (`docker builder prune
  --filter until=168h`), automatic tier acceptable because it is regenerable by definition; volumes = dangling AND no container reference AND older than 30
  days, review tier only (a volume can hold the only copy of data). Never `docker system prune --volumes`.
- Effort M. C: space only returns after compaction (admin), so the feature must say so instead of promising GB.

## 3. uv cache when locked
- Measured: `%LOCALAPPDATA%\uv\cache` 31.66 GB before / 29.45 GB after `uv cache prune` (2.2 GiB removed, 63,226 files, lock was free,
  `UV_LOCK_TIMEOUT=120`, no `--force`). `archive-v0` is 31 GB of unpacked wheels.
- VERIFIED today: any live `uv run`/`uv pip`/`uv sync` holds a shared lock on `.lock` for its lifetime; `prune`/`clean` need the exclusive lock. #133 (sign-in
  retry) addresses the weekly task; it is not on main yet (GG merge batch).
- Feature: let the regenerable tier choose `uv cache clean` (not just `prune`) when C: usage is above the user's alert threshold; `clean` is hardlink-safe for existing
  venvs (their files stay) and costs only a redownload. Today `prune` returns ~7 % of the cache.
- Safety rule: exclusive lock obtained within the bounded wait, never `--force`, never while any `uv.exe` is alive; skip and report otherwise.
- Effort S.

  not session dirs (owner unknown, left alone). ~13 GB are single `.output` task logs (1-5 GB each) inside sessions that are LIVE: cannot be touched.
- Feature: a regenerable-tier category `agent_scratch` for session dirs only: `<project>\<uuid>` directly under `%TEMP%\claude`, project not on the exclusion list,
  newest file content older than 7 days, no running process whose command line mentions the uuid, no reparse points (junctions inside must be listed and rejected, a
  verified past hazard: one scratch held 37 junctions).
- Effort S (reuses #110's newest-content age, #139's per-directory pattern and the exclusion machinery). Off by default, same ownership caveat as pytest temp.

## 5. Stale agent clones and worktrees
- This engagement: 36 git worktrees of one repo, ~0.45 GB each; 12 + 22 were removed after proving every commit was on a remote ref or in a merged PR (see RESUME.md),
  10 got `backup/<worktree>` branches first.
- Feature: review-screen "stale worktrees" list for repos under the project roots (`git worktree list --porcelain`).
- Safety rule: not the main checkout, not on the exclusion list, `git status --porcelain` empty (EOL-only noise counts as clean only if `git diff --ignore-cr-at-eol` is empty),
  every commit reachable from a remote-tracking ref (`git rev-list HEAD --not --remotes` empty), no stash, no lock file, no process with that cwd. Removal uses
  `git worktree remove` (never `rm -rf`) and keeps the branch.
- Effort M. Never automatic.
