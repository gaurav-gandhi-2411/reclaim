# Reclaim Pre-Build Audit — 2026-08-20

## SHIPPED DEFECT — headline finding, not a footnote

**A real deletion path shipped to `main` with zero identity re-verification and stayed there for 29 days before this engagement found and fixed it.**

- **What**: `api/service.py::_build_user_selected_candidate` — the code path behind the dashboard's
  AI Suggestions tab (a user or an AI-ranked suggestion selecting a specific path to delete/vault)
  — built a `Candidate` from a fresh stat at *selection* time, then handed it to `apply_batch`,
  which performed the real mutation with no re-check that the path still pointed at the same
  object by the time the mutation actually ran. On `main` before this engagement's fix,
  `apply_batch`/`run_apply` didn't even accept a `scan_index` parameter — the re-verification
  mechanism this finding demanded didn't exist anywhere in the shipped code.
- **Exposure window**: introduced in PR #2 (`feat(api): wire the AI layer into the dashboard as
  a recommend-only AI Suggestions tab`), merged **2026-07-23T12:32:11Z**. Closed by PR #45
  (`fix/apply-batch-identity-reverify`), merged **2026-08-21T09:58:58Z**. **29 days live on
  `main`**, reachable by any real user clicking a real AI-suggested delete/vault action through
  the actual shipped dashboard — not a theoretical code path, not confined to an unmerged branch.
- **Reproduction** (live-reproduced this engagement, real NTFS, not simulated): scan a directory,
  let a candidate get selected via the AI-suggestion path, then — before the apply actually
  executes — swap the content at that exact path (delete-and-recreate with different content, or
  repoint an NTFS junction to a different target). The path string is unchanged, so nothing in
  the pre-fix pipeline detects the swap. The swapped content gets permanently deleted (direct-
  delete categories) or moved into Reclaim's own vault under the wrong batch (vaulted
  categories) — real, unrecoverable action on content the user never selected.
- **How it was found**: not from auditing this specific code path directly — found by first
  demonstrating the same defect class against the not-yet-merged MCP server (PR #39, task J5b),
  then explicitly checking (task N4) whether any *already-shipped* code path had the identical
  gap. It did.
- **Fix**: PR #45, merged to `main`. A single identity-verification choke point inside
  `apply_batch` (`(dev, ino)` re-check via `os.stat(follow_symlinks=False)`, hybrid vault-
  downgrade for large candidates, post-condition verification, real vault reconciliation) now
  covers this path along with CLI apply, HTTP `/api/apply`, and the future MCP `delete` — all
  four converge on the same function, so this fix closes all of them at once, not just the one
  that was found first.

## VERIFICATION GAP — the frozen artifact was never systematically tested, second headline finding

**Every P0 fix and every R-series feature landed on `main` with zero frozen-artifact verification in CI or any gate — the only real check against the actual compiled binary was one ad hoc manual smoke test this session, and it found bugs by accident, not by coverage.**

- **What**: `scripts/verify.py` and every eval/CI gate in this repo (including
  `evals/test_apply_batch_call_graph_gate.py` and `evals/test_apply_identity_reverify.py`, the
  gates the P0-K1a identity-reverification fix depends on) run exclusively against Python source
  (`python -m reclaim` / `pytest`). None of them execute the Nuitka `--standalone` frozen binary.
  Two real, live-reproduced bugs existed ONLY in the frozen build and were invisible to every
  green CI run and every "all gates pass" report throughout this engagement:
  1. Toast notifications: `ModuleNotFoundError: winrt.windows.foundation` — Nuitka's static
     import-following missed a PEP 420 namespace package reached only via a native `.pyd`'s
     C-level import. Fixed PR #49.
  2. TEMP-cache detection: silently proposed zero candidates on any account where `%TEMP%`
     resolves in 8.3 short-name (DOS alias) form, because the scanner always indexes real
     long-form paths. Fixed PR #50.
- **Exposure**: the one real frozen build on disk (`packaging/dist/reclaim-setup.exe`,
  330,937,412 bytes, SHA-256 verified, real wall-clock build completed 2026-08-22 06:47 local)
  already contains the source for every P0 fix that had merged before it (#36, #39, #41, #43,
  #44, #45) and both R-series features (#37, #38) — but at no point did any of those PRs' own CI,
  merge gate, or "all gates green" report reflect a single frozen-binary execution. The identity-
  reverification property PR #45 proves via `evals/test_apply_identity_reverify.py` (K1's six
  teeth-proofs) has never actually been exercised against the compiled `os.stat`/`ctypes` call
  path it depends on at runtime — only against source.
- **How it was found**: not from a systematic sweep — found only because this session happened to
  run one manual fresh-install smoke test (U1–U6, X1–X3) on a disposable Windows account
  (`ReclaimSmokeTest`). The two bugs found are, by construction, exactly the two whose code paths
  happened to be exercised during that specific manual test's actions — not the product of a
  deliberate coverage plan. A frozen-vs-source risk audit (Y2) found other Nuitka-sensitive code
  paths — protocol handler resolution, Task Scheduler registration, the DPAPI key store, MCP
  server startup — that had never been exercised against the frozen binary at all, in either
  direction; clean or broken was genuinely unknown until a dedicated smoke suite existed to check.
- **Fix**: a frozen-artifact smoke suite (Y3/Z2, `packaging/smoke/run_frozen_smoke_suite.ps1`) now
  exists as a single-command, pass/fail-per-check harness intended to run against every future
  installer build. See the Phase 4 section below for its actual coverage, results, and residual
  gaps once run.

## STALE-BASE VERIFICATION GAP — "green" meant green against a snapshot, not against reality, third headline finding

**A real signature regression on PR #50 was reported green three separate times, by three separate checks, because every one of them ran against a stale `main` rather than re-deriving it fresh — the same defect class as the stale-index deletion P0 (N4): trust placed in a snapshot's truth at the moment of *acting*, not just at the moment the snapshot was taken.**

- **What**: PR #50's own new end-to-end regression test called
  `detect_temp_and_browser_caches()` with its pre-PR-#46 signature. PR #46 (merged first, in the
  same batch) added `min_temp_root_age_hours`/`now` as required keyword-only parameters. PR #50's
  branch was cut before #46 merged and was never rebased onto post-#46 `main` before any of the
  three times its own greenness was reported:
  1. The original Y4 batch report: "PR #50 ready — no conflicts... full suite green (1055
     passed, 88.45% coverage), CI 6/6" — run against the branch's original base, before #46/#47
     had even merged to `main` yet.
  2. The same claim, restated verbatim in the consolidated 5-PR merge-readiness report handed to
     GG — a re-statement of check #1's result, not a fresh check.
  3. Z1's own `scripts/verify.py` run while adding the env-var normalization gate — a genuinely
     *fresh* local test run (1060 passed), but still against the branch's stale base, because
     Z1's task began from the (by-then-false) premise "no conflicts" instead of doing
     `git fetch && git rebase origin/main` first. The regression was invisible to this run for
     the same structural reason it was invisible to the first two: the branch had simply never
     been pointed at post-#46 `main`.
  The regression was only found on the fourth check — a real `git rebase origin/main` executed
  immediately before this session's own merge-readiness claim for PR #50, per AA1's process fix
  below — which is also the first of the four that actually satisfies "verified against current
  reality" rather than "verified against a remembered/inherited state."
- **Why this matters beyond one test**: this is not "a rebase was skipped" as an isolated
  slip — it is the exact same **verify-a-snapshot, act-on-a-different-reality** shape as N4 (the
  29-day-exposed apply-time TOCTOU defect): a claim ("this candidate is safe to delete" /
  "this branch is safe to merge") was true when checked, and silently stopped being true by the
  time it was acted on, with nothing in the process that re-checked at the point of action. N4's
  fix was a re-verification choke point immediately before mutation; the same shape applies here.
- **Process fix**: a branch's tests, coverage, or CI status may only be reported as "green" /
  "merge-ready" immediately after an explicit, freshly-run `git fetch origin && git rebase
  origin/main` (or equivalent proof the branch's parent commit *is* current `main`'s tip) in the
  same task that makes the claim — never inherited from an earlier check, however recent, and
  never assumed from "no conflicts were reported last time." This session's post-AA1 fix applies
  this exactly: `feat/frozen-artifact-smoke-suite` was rebased onto `main` tip `32a1c19` and
  re-verified fresh (1076 passed, `config.py` 97.83%) before being called green, rather than
  trusting its pre-existing dry-run result.
- **CODA, same session, same finding, recurred anyway**: PR #51's own "1152 passed, 94.41%
  coverage" verification report was ITSELF computed against a stale base — this orchestrating
  session's local `main` branch ref had been fast-forwarded once (during Z1) and never again,
  so it sat at commit `990ee16` (post-#47, pre-#48/#49/#50) for the rest of the session. Creating
  `fix/protocol-handler-log-path-cwd-independent` via `git checkout -b` from that stale local
  `main` silently branched from the wrong parent; the local `scripts/verify.py` run that produced
  the reported numbers never actually exercised #48/#49/#50's source, tests, or gates. No real
  damage resulted — GitHub's server-side merge correctly three-way-combined the non-overlapping
  changes, and `main`'s own post-merge CI (triggered independently by the push, `2026-08-22
  14:15:38Z`) confirmed the true merged state is genuinely green — but the *reported* number was
  not evidence of what it claimed to be evidence of, and this was caught only by accident (a
  routine `grep` while wiring AB1's own gate came back empty where it should have found #50's
  entry). This is exactly rule 85a's "a control built specifically to catch reach failures having
  a reach failure on its own first run" pattern, one level up: writing the rule down in this same
  document, in this same session, did not prevent the identical mistake minutes later, because
  the failure mode isn't "forgetting the rule exists" — it's "not re-deriving the fact the rule
  depends on" (here: whether the local `main` ref actually matches `origin/main`) at the moment
  it matters. Fixed going forward the same way: `git branch -f main origin/main` after every
  fetch, and the affected branch (`fix/data-path-cwd-independence-siblings`, AB1) was rebased
  onto the real `origin/main` before its own verification numbers were trusted.

## R5's SCHEDULED-DELIVERY PATH IS UNVERIFIABLE IN THIS ENVIRONMENT — disclosed, not silently accepted

**The Task Scheduler action that periodically fires the disk-space toast (R5's actual delivery
mechanism, not just its decision logic) cannot be end-to-end verified on this machine — the gap
is structural to the test environment, not a defect found and left unfixed.**

- **What was verified**: the registered action's exact command line (`reclaim.exe
  check-disk-space`, no `--config`/`--state` override) run with its configured
  `<WorkingDirectory>` (confirmed present in `packaging/reclaim.iss`'s generated Task XML) does
  NOT hit the CWD-relative crash class PR #51/AB1 fixed elsewhere — live-verified by running the
  identical command+CWD combination under `ReclaimSmokeTest`: `status=ok reason=disabled
  percent_used=None threshold=80.0`, exit 0. The task registration itself is sound.
- **What could not be verified**: whether a real on-demand or scheduled invocation actually
  *executes* under this task's `LogonType=InteractiveToken` setting when triggered outside a
  genuine interactive logon. `schtasks /run /tn "Reclaim Disk Space Check"` reports `SUCCESS`
  but `Last Run Time`/`Last Result` never change (stays at the `267011` "has not run" sentinel),
  and zero Task Scheduler operational-log events are recorded for the task at all — diagnosed as
  `runas /savecred` not producing a session Task Scheduler's `InteractiveToken` check recognizes
  as "logged on" (no `Win32_LogonSession`/`Win32_LoggedOnUser` association observed for
  `ReclaimSmokeTest` either), not a product defect.
- **Is `InteractiveToken` the right choice?** Yes — kept as-is, not changed. The task's entire
  purpose is a *visible* toast, and Windows toast rendering itself requires a real interactive
  desktop session regardless of Task Scheduler's logon type; switching to a non-interactive logon
  type (e.g. S4U) would make the task run even when nobody is logged in — a real behavior change,
  not a neutral one — while still not verifying the thing that actually matters (toast delivery,
  which still needs a real interactive session either way). It would only make an unrelated proxy
  metric (`Last Run Time` advancing) testable, which is not the same as verifying the feature.
- **What would actually close this gap**: a genuine interactive console login as
  `ReclaimSmokeTest` on this machine (Fast User Switching — Win+L or Start menu → account icon →
  "Switch user", NOT "Sign out", to keep the primary session alive concurrently; this machine is
  Windows 11 Home, which does not support incoming RDP as a host, so Switch User is the only
  practical route). Requires the account's actual password, which was set interactively when the
  account was created and is not something this session has visibility into (only the
  Credential-Manager-cached form used by `runas /savecred`) — genuinely a step for GG to perform,
  not something to route around. Once logged in: `schtasks /run /tn "Reclaim Disk Space Check"`,
  then re-check `Last Run Time`/the Task Scheduler operational log, and optionally lower
  `disk_threshold_percent` in that profile's `config.toml` temporarily to force a real toast and
  visually confirm delivery + a working Snooze button.

## CROSS-TENANT BLAST RADIUS — a non-admin scan could reach other users' files by default, headline finding

**SIMPLE mode's default "Clean My Computer" action scanned every fixed drive from its volume
root, with zero ownership check anywhere in the codebase — a real smoke-test scan by a non-admin
local account classified 13,927 of 13,991 `dev_artifacts` candidate paths as belonging to OTHER
users' unrelated projects, deletable only because of broad ACLs at the volume root.**

- **What**: `POST /api/scan/full-drive` (`reclaim.drives.list_fixed_drives` +
  a volume-root-anchored scan) was SIMPLE mode's default action reached by a single click — no
  ownership/home-directory scoping existed anywhere between "user clicks Clean My Computer" and
  candidates being generated and offered for deletion.
- **Exposure**: found live, on a real multi-project dev machine, via a real fresh-install smoke
  test (`ReclaimSmokeTest`, a disposable non-admin local account). The scan reached other real
  users' profile directories and other projects' `dev_artifacts` (node_modules, build caches,
  etc.) purely because NTFS ACLs at the volume root granted broad Modify rights, not because the
  scanning account had any legitimate claim on that content.
- **How close to a real deletion**: only agent-level discipline during the smoke test (explicitly
  excluding `dev_artifacts` from the actual apply step) prevented real deletion of another user's
  files during this engagement. Nothing in the product itself would have stopped it.
- **Fix**: PR #47. `reclaim.api.service.user_scan_roots()` now returns `[Path.home()]` by
  default — SIMPLE mode's "Clean My Computer" scans only the invoking user's own profile. A
  whole-drive scan remains available but only as an explicit, separately-surfaced opt-in gated
  behind its own confirmation dialog, never the action a single click reaches. Proven structurally
  (`evals/test_scan_scope_gate.py`, a sibling-profile fixture proving zero candidates ever reach
  another user's directory-walk level, not just filtered after the fact) as well as functionally.

## 8.3 SHORT-NAME SILENT ZERO-YIELD — TEMP-cache detection returned zero candidates, permanently, with no error, headline finding

**On any account whose Windows profile path is long enough to trigger an 8.3 short-name (DOS
alias) — a real, live-reproduced condition, not a hypothetical — TEMP-cache detection silently
proposed zero candidates, forever, for that user, with nothing anywhere indicating a problem.**

- **What**: `os.environ.get("TEMP")` can return Windows' legacy 8.3 short-form alias (e.g.
  `C:\Users\RECLAI~1\AppData\Local\Temp` for the 16-character username `ReclaimSmokeTest`) even
  when other profile-relative env vars (`%USERPROFILE%`, `%LOCALAPPDATA%`) correctly resolve
  long-form on the SAME account — confirmed live this session, not inferred. The scanner always
  indexes real long-form paths (`FindFirstFileW` never returns 8.3 names), so a `temp_and_
  browser_caches` detector pattern built from an unresolved short-form value could structurally
  never match anything in the index. `detect_temp_and_browser_caches` proposed zero
  `windows_temp` candidates — not an error, not a warning, just silently nothing, indefinitely.
- **Fix**: PR #50. `config._resolve_long_path` (`GetLongPathNameW` via `ctypes`) wired into the
  single `_win_path` chokepoint every config-default env-var read already routed through — the
  fix therefore already covered every affected env var (`LOCALAPPDATA`, `USERPROFILE`, `TEMP`),
  not just the one confirmed-affected one, because it landed at the chokepoint rather than as a
  TEMP-specific patch. Proven with a real `GetShortPathNameW` round-trip teeth-proof
  (`tests/test_config.py`), not a hand-authored fake short name.
- **The same defect class recurred immediately, elsewhere**: PR #51 found the identical bare-
  CWD/env-relative-path fragility in `logging_config.DEFAULT_LOG_PATH` (a different symptom —
  a crash, not a silent zero-yield — same root shape: an environment-derived default that breaks
  under a real invocation context the original author didn't anticipate). AB1 generalized that
  fix to nine more modules (`mode.py`, `first_run.py`, `executor.py`, `api/app.py`,
  `mcp/server.py`, `cli.py`, `anthropic_key_store.py`, `ai/clutter_ranker.py`, `ai/
  category_explainer.py`, `notifications.py`) that independently built the same pattern — see
  PR #52/#53 and `evals/test_data_path_cwd_independence_gate.py`.

## TEST-HARNESS CONTAMINATION — observations from a probed profile are not observations of a user's experience, methodology finding

**Two separate, real findings this session were corrupted by the SAME root cause: this session's
own probing activity altered the exact state a later step tried to observe, before that
observation happened.** Neither was a product defect. Both were caught only by chance — a
directly-checked `localStorage` value in one case, a directly-checked `/api/first-run` response
in the other — not by any structural safeguard that would catch the next instance of this shape.

- **Instance 1 (AE2)**: a real browser session was used to observe "what does a first-time user
  see", and it reported the dense Advanced view as the default. The actual cause: that browser
  profile already carried `localStorage["reclaim-dashboard-mode"] = "advanced"` from THIS
  session's own earlier navigation to the same `127.0.0.1:8420` origin, on the same reused Chrome
  profile the tooling keeps across the whole engagement. The template's real default (`data-mode
  ="simple"`) was never actually being tested — a stale preference from a previous, unrelated
  probe was.
- **Instance 2 (residual gap #6 below)**: `ReclaimSmokeTest`'s `/api/first-run` has returned
  `{"acknowledged": true}` every time it's been checked this entire engagement. The genuine
  first-run screen — what a real first-time user sees before ever touching the product — has
  never actually been observed, because some earlier interactive session on this exact profile
  (traced as far as: `app.js` only calls `POST /api/first-run/acknowledge` on an explicit button
  click, never automatically on page load — so a real click happened at some point, not merely a
  page load) already consumed the one-time flag before any deliberate "observe first impressions"
  step was attempted.
- **The general shape**: any state that persists ACROSS separate probing sessions on the same
  target (browser `localStorage`, a one-time server-side flag file, an accumulated scan index) is
  invisible contamination risk for any LATER step that assumes it's observing a clean baseline.
  The two instances above happened to be caught because each one was checked directly against its
  real value before being trusted — but neither the frozen smoke suite nor this session's own
  browser-based checks had any BUILT-IN safeguard against this; it was caught by habit, not by
  design.
- **How the frozen suite avoids this going forward**: `packaging/smoke/run_frozen_smoke_suite.ps1`
  does NOT currently reset or check application-level state (first-run flag, browser storage)
  before running — confirmed by inspection: none of its checks reference `/api/first-run` at all,
  and it has no browser-automation step of its own. This is a real, disclosed gap, not yet fixed
  in the suite's own code. The PROCESS discipline adopted for AC2 instead: on the newly-reinstalled
  profile, the genuine first-run screen is observed via a **freshly-cleared browser context**
  (storage cleared before the first navigation) as the FIRST action taken against that profile —
  before the frozen suite's own automated checks run, before any CLI command, before any other API
  call — since that observation has exactly one chance to be real. A more durable fix for the
  suite itself (out of scope for this pass, noted for later): the harness could verify
  `/api/first-run` reports `false` before its own checks begin, and refuse to proceed (or clearly
  flag the run as "state already contaminated") rather than silently running against a
  profile whose first-run flag reality is unknown -- the same "fail closed on unverifiable state"
  principle rule 98a already applies to other guards in this codebase.

## Task D — Proposals

### D1. ML feature evaluation

**(a) Regeneration-cost prediction from re-download/rebuild history — DEFERRED-PENDING-INSTRUMENTATION** (reclassified from REJECT per Phase-2 correction). No observed
history exists to train on today, and regen cost is largely deterministic per category already
(`rebuild_instruction`/`recovery_cost_note` in `models.py` are effectively a hand-authored
lookup table) — a trivial per-category constant is very likely already near the achievable
ceiling. Reclassified rather than rejected outright because the *reason* it can't be built isn't
that the idea is bad, it's that the instrumentation (logged re-download/rebuild events) doesn't
exist yet — a REJECT implies "don't build this," DEFERRED means "revisit once the logging exists
and there's real history to evaluate a model against a trivial baseline with."

**(b) Staleness/reuse-probability from access-time telemetry — DEFERRED-PENDING-INSTRUMENTATION**
(reclassified from REJECT per Phase-2 correction; see the USN-journal finding below). The
codebase already made a deliberate call here: `index.py`'s `is_unchanged` explicitly never
consults NTFS atime (confirmed in PLAN.md's Stage 2 notes), because
`NtfsDisableLastAccessUpdate` defaults ON on Windows — atime is unreliable on this exact
OS/filesystem, and no model should be built on it. That part of the original reasoning stands.
**USN Change Journal evaluated as the substitute signal, per instruction — empirically tested on
this machine, not inferred:**
```
IsElevated=False (confirmed via WindowsPrincipal.IsInRole(Administrator))
> fsutil usn queryjournal C:        → succeeds, exit 0, returns journal ID/USN range/size metadata
> fsutil usn readjournal C: csv     → Error 5: Access is denied.
```
**The split is real and matters**: querying the journal's *metadata* (does one exist, its ID,
current USN range) works fine unelevated — but actually *reading change records* (the only part
useful for a staleness/reuse-probability signal — "was this path touched since date X") requires
elevation, confirmed by direct reproduction, not documentation lookup. The underlying reason is
structural: `FSCTL_READ_USN_JOURNAL` requires the same raw-volume-handle access Windows gates
behind backup/restore privilege or Administrator rights, independent of the calling user's own
file permissions.
**Conclusion: USN is not usable as a background-service or scheduled-task signal under Reclaim's
current architecture** — using it would mean asking the user to run Reclaim elevated, which
conflicts directly with `elevation.py`'s existing, deliberate "never run elevated" invariant
(Task B7). This forecloses USN as a *routine* substitute for atime. If staleness-based ranking
is wanted later, the consistent path is an explicitly-elevated, opt-in, one-time diagnostic
(mirroring how Track A routed the all-SIDs Recycle Bin step to the user rather than
self-elevating), not continuous polling. Still deferred, not rejected — worth revisiting only if
an opt-in elevated diagnostic mode is ever built for other reasons.

**(c) Learned classifier for the residual "other" bucket — CONDITIONAL, defer.** This audit
found the "other" bucket isn't even measured yet (P1 above) and the real gap is structural
(one-level-deep attribution) plus config coverage (npm/HF/conda paths), not a classification
problem. Fix the structural roll-up and close the known config gaps first, *then* measure what
residual actually remains. If a meaningful residual survives that, a lightweight classifier
with a hard confidence floor (below which it falls back to "unclassified," never a guessed
label) is reasonable — and the existing `ai/labeling_app.py`/`ai/labeling.py` gold-set tooling
is directly reusable for building training data. Eval metric: accuracy vs. a held-out labeled
sample, must clear a majority-class baseline. Don't build this before the cheaper fixes.

**(d) Growth forecasting for days-until-full — CONDITIONAL, defer further.** R5 (the alert this
would feed) doesn't exist yet — ship the zero-ML threshold-crossing notification first. Once
R5 ships and the tool has logged periodic real disk-usage snapshots (which it doesn't today),
a simple linear-trend fit is very likely sufficient; no case for a complex model here. Can't
be usefully evaluated until real usage-history data exists, so this is a post-launch item, not
a blocker.

**Bottom line**: none of the four proposed ML features clear "does this improve user outcomes
more than the non-ML fixes already found." The highest-leverage work in this audit is
non-ML: fix P0-1 (categories off by default) and P0-2 (uncached dedup hang).

### D2. UX changes that most reduce time-to-first-reclaimed-GiB

1. Ship sane default-enabled categories (or a bundled default config) — this single change
   turns "0 results forever" into "real results on first scan," the single biggest lever
   available right now (P0-1).
2. Fix the 5-call-site uncached dedup hang (P0-2) — a dashboard that hangs or 500s before a
   user reaches the clean button actively damages this metric regardless of what else ships.
3. Add an in-app Settings/category-toggle tab — removes the "hand-author TOML" barrier;
   naturally pairs with R2's proposed key-entry UI as one new surface, not two.
4. Close the three confirmed config coverage gaps (npm path, HF datasets/xet, conda pkgs-dir) —
   directly increases "GiB found" on a very large fraction of real developer machines, since
   npm and HF caches are extremely common.
5. Surface `build_one_click_summary`'s output as the first thing shown after a scan completes,
   rather than requiring a tab switch from an initially-empty Overview.

### D3. Where I'd deviate from the brief

- **Sequence R7 (MCP control surface) after the P0 fixes, not alongside them.** An agent
  control surface over a product that currently deletes nothing by default and can 500 on its
  own dashboard is premature — the MCP server's value is entirely downstream of the product
  actually working for a human first.
- **Don't ship unattended/scheduled auto-apply as part of R6** until the live-process-lock and
  hardlink-into-active-install checks exist (P0-3) — ship the allowlist as "one confirming click
  required" first (it's already close to this via `build_one_click_summary`), add true
  autonomy only after those two checks land.
- **Fix P0-5's discoverability gap immediately** — it's a one-line docstring cross-reference or
  a file move, essentially free, and closes a real audit-trail gap around the most
  safety-critical test in the repo.
- **Add three new deterministic (non-ML) detector rules directly motivated by this session's own
  real-disk findings**, all cheap and rule-based: (i) an archive sitting next to its own already-
  extracted contents (the 28.69 GiB Kaggle zip pattern), (ii) `.incomplete`-suffixed interrupted
  downloads (the 24.68 GiB AetherArt pattern — never usable, zero regeneration-cost concern),
  (iii) a `node_modules`/`.venv` that's a duplicate of the identical directory in a sibling git
  worktree of the same repo. All three are deterministic, need no ML, and directly reclaim real
  GiB matching this user's own actual portfolio structure — likely generalizable to many

## AR1 — what the AE1 teeth-proof actually established versus what it was read as establishing

**Both the AC2 "AE1 correctly skips outside-home paths" finding and AN5's contradiction of it are
real. The earlier proof was not wrong about what it tested — it was read as proving something
broader than its own test configuration covered.**

- **What the AC2 proof actually established, precisely**: "a candidate at a synthetic path outside
  `Path.home()`, applied against an `AppState` whose `scan_status.root is None` (the fresh-process
  default), is correctly skipped with `skip_reason: outside_user_scope`." That sentence is still
  true today, unchanged by AN5 — re-run, it still passes.
- **What it was read as establishing, in this document's own words**: "AE1's `check_within_
  allowed_scope` applies uniformly to every candidate regardless of selection path" (Phase 3/AO1's
  sibling sweep) and "A POST to `/api/apply` for a path outside `Path.home()` correctly returned
  `skip_reason: 'outside_user_scope'`, zero bytes touched" (AC2, unqualified) — both true of the
  tested configuration, both silently generalized to "outside-home paths are blocked," full stop.
  The gap between those two statements is exactly the `scan_status.root is not None` case: a
  long-lived, multiply-reused server process realistically spends most of its life in, not
  outside, that state, since any user who has ever done one legitimate outside-home scan leaves
  the process in it permanently (pre-AN5).
- **The general lesson**: a VERIFIED tag in this document means "an agent or the verifier actually
  read the code or ran it" — it does NOT mean "ran against every state the real code can be in."
  A synthetic-fixture proof is real evidence for the fixture's exact configuration; treating it as
  evidence for the whole state space it resembles is the same shape of over-generalization as
  rule 85a/85b's control-surface gap, one level up: not "the control doesn't cover what it claims"
  but "the claim itself was phrased more broadly than the control's own test actually covered."
  Rule 101a's "absence in a sampled sweep is not evidence of absence in the full record" is the
  closest existing rule to this — this is that same principle applied to a single-path functional
  proof rather than a search sweep.
- **What this implies for every other VERIFIED entry in this document proven on one synthetic path
  or fixture rather than derived from reading the full branch structure of the code under test**:
  every such entry should be read as "proven for that configuration," not "proven in general,"
  until re-checked. Not re-audited wholesale here (a much larger task than this finding warrants
  on its own), but naming the entries with the same proof shape so a future pass knows where to
  look first, rather than starting from a blank slate:
  - PR #47's cross-tenant scope-filtering proof (`evals/test_scan_scope_gate.py`) — "a sibling-
    profile fixture proving zero candidates ever reach another user's directory-walk level" is one
    fixture shape (two sibling profiles, one scan). Worth checking whether it, too, only exercises
    a fresh `scan_status.root is None` state, the same gap AN5 just closed for the apply-time
    check specifically.
  - PR #39/G2's MCP TOCTOU proof — already the most honestly scoped of the group ("verified line-
    by-line, no residual gap found or constructible for the specific race it targets... cross-
    surface concurrency... remains a separate, theoretical, explicitly out-of-scope gap" is stated
    directly in this document already), included here only for completeness, not as a new concern.
  - The K1a identity-reverification "six teeth-proofs" — proven against specific real files/
    hardlinks on this one machine; likely fine (identity re-verification is inherently per-file,
    not state-space-dependent the way scope authorization is), but not independently re-confirmed

  - AC2's own remaining checks (1b, 1e, 4) already carry exactly this caveat explicitly (AJ1: "an

## AU2 — Step 7's app-reported-vs-measured discrepancy was the diagnostic script, not the product (2026-08-24, resumed session)

**Resolves RESUME.md's open Step 7 item.** Two script bugs in `packaging/smoke/
ac3_login_diagnostic.ps1`'s Step 7 (S2/U4), each producing a plausible-looking wrong number rather

- **Bug 1 — a reference-equal, live-backed `PSDriveInfo` object read twice.** `Get-PSDrive -Name C`

  what the apply actually freed.
- **Bug 2 — batch-level method logged as if it were per-item.** The log line read

  FINDING, NOT A SCRIPT BUG."
- **Status of the underlying product claim (AV1, this session): BELIEVED, not yet VERIFIED.** The

## AV2 — apparatus-reliability finding, extended: this harness's failure mode is silently-wrong values, not loud failures

**AN3 already established the harness has produced more defects than the product this session.
AU2 sharpens what kind of defect**: neither of the two bugs above raised an exception, timed out,
or produced an obviously-malformed value — both produced a *plausible* number (`0 bytes freed`
reads as a legitimate measurement; `method: recycle_bin` reads as a legitimate method name) that
was simply wrong. This is why three independent isolation checks (source call, curl dry-run, curl
real apply) could all agree the underlying logic was correct while the full trip script kept
disagreeing: an isolation check re-implements the measurement freshly each time (no reused object
to go stale), so it never hit either bug; the trip script's *specific* variable-reuse pattern is
what triggered bug 1, and its own comment-writer's correct mental model of the fix ("retention_days
=None -> auto-resolves to direct_delete") is what led bug 2's misleading batch-level readout to be
believed rather than doubted.

**What would catch this class going forward, generalized beyond this one step**: any diagnostic
step comparing a live-measured value against an app-reported one should also assert the
*fixture's own expected value* as a known constant wherever the fixture size is fixed and known
(here: a 10MB fixture should show `bytes_freed` in `[10485760 * 0.98, 10485760 * 1.02]`
independent of what the OS-measured side says) — a wrong reading on EITHER side then fails loudly
against a fixed expectation, rather than two possibly-wrong numbers being compared only to each
other and agreeing by coincidence (or, as happened here, disagreeing for a reason that had nothing
to do with what the check was meant to verify). Not implemented as part of this pass — noted as
the concrete mechanism, for whoever next touches this step or writes a similar one.

## AY1 — R5's actual delivery mechanism has never registered, on any install, since the feature shipped — headline finding, not a footnote

**The disk-space-threshold toast notification (R5) has been undeliverable by its own designed
mechanism (a per-user Task Scheduler entry) on every single install this feature has ever shipped
in, for its entire life. "Task Scheduler unregistered" was read, across many sessions and many
trip runs, as an expected environmental limitation of this specific dev machine — it was a real,
live, 100%-reproducing product defect the whole time, misattributed.**

- **What**: `RegisterDiskSpaceTask` (`packaging/reclaim.iss`) builds a task-definition XML whose
  header declares `encoding="UTF-16"`, then writes it via `SaveStringToFile`, whose second
  parameter is `AnsiString` — Inno Setup's Pascal Script silently narrows the Unicode `XmlContent`
  to the system ANSI/UTF-8 codepage at that call, so the file written to disk was always
  single-byte-per-character bytes, never real UTF-16, regardless of what its own declaration
  claimed. `schtasks.exe /create /xml` trusts the declared encoding over the actual bytes and
  fails outright (`ResultCode 1`) against a mismatched file — and this specific failure was
  silently swallowed by design: the function's own comment states "a failure here... is not
  surfaced... a best-effort convenience registration, not a required install step." That posture
  is defensible for a genuinely occasional environmental failure; it is not defensible for a
  failure with 100% reproduction across every install, which is what this always was.
- **Exposure range**: introduced in PR #38 (`feat: 80%-threshold disk-space toast notification
  (R5)`), merged **2026-08-21T08:41:53+0530** (commit `6552ed6`). Never fixed until PR #83
  (`fix/scheduled-task-xml-utf16-encoding`), merged **2026-08-24** (this session). **Every real
  install run against every rebuild in that window — at minimum rebuilds #2 through #6, and every
  one of the 12 real AC3 trip runs logged in `C:\Users\Public\reclaim_ac3\` across 2026-08-23 and
  2026-08-24 — registered zero working scheduled task.** This is a pre-launch engagement with no
  external users yet, so the honest claim is "100% of this engagement's own real installs," not
  "affected real users" — but had this shipped to an actual user in this window, their disk-space
  notification would silently never have had a delivery path, with nothing in the product itself
  to tell them so.
- **The misattribution, stated plainly**: this document's own AS4 entry, written earlier in this
  same engagement, reads *"3 ABORTs (Task Scheduler unregistered, the two growing-index timeouts
  from AS3)"* in a tone that groups a real, 100%-reproducing product defect with two already-
  understood, already-disclosed apparatus timing issues — as if all three belonged to the same
  "known, environmental, not worth chasing" category. They did not. The Task Scheduler ABORT was
  never actually investigated to a root cause in any of those earlier passes; it was pattern-
  matched against this engagement's own genuinely-environmental findings (the machine's disabled
  Task Scheduler operational log, `ReclaimSmokeTest`'s credential/session issues) and folded into
  the same bucket without being tested against the null hypothesis "the registration might
  actually be broken." AY1 (this session) is what finally asked that question directly and
  reproduced the real mechanism live, isolated from every other confound (a real Nuitka+Inno
  rebuild was not even needed to prove it — a same-day ISCC-only recompile against the existing
  Nuitka dist was sufficient, see PR #83).
- **What would have caught this earlier**: the frozen smoke suite's own check 5 (`packaging/smoke/
  run_frozen_smoke_suite.ps1`) was already structurally capable of catching this — it queries the
  real task, runs it on-demand, and asserts `Last Run Time` actually advances, which is a correct,
  sufficient test of "does this registration genuinely work." Its failure mode was never a design
  gap; it was that a `schtasks` query failure was reported as **BLOCKED** ("most likely no
  installer has registered it on this machine") rather than investigated as a candidate **FAIL**
  every single time it fired. **BLOCKED and FAIL read identically in a quick scan of a summary
  line ("PASS: 7 FAIL: 1 BLOCKED: 5") unless someone deliberately asks, of every BLOCKED result,
  "is this genuinely blocked by environment, or is `it hasn't run` doing the same job a false
  green would do elsewhere" — the same rule-85a "what surface does this control actually reach"
  question, applied to a BLOCKED verdict instead of a PASS.** Now that AY1's fix is in `main`,
  check 5 has a real chance to reach PASS/FAIL against a genuinely-working registration for the
  first time in this engagement's history — confirming that in AX4/AZ4's rebuild #7 dry run is

## BD1 — the real AC3 trip: Task Scheduler ABORT root-caused, and it is not AY1 recurring

  single time, not as a race or as machine-local corruption of the kind AY1's original retry logic
  was written to tolerate. This explains every one of the ~20 historical AC3 trip runs hitting
  this exact ABORT, on a machine where gaura's own account happened to register the same task name

  Windows PC where a second, non-admin user installs Reclaim after a first user already did will
  hit the identical silent failure — the disk-space alert simply never registers for the second
  account, with nothing telling them why.

## BE2 — scan-initiation events now go to a dedicated, isolated audit log

**BD4 fixed WHAT Step 9 copies (all `reclaim.log*` files); it did not fix WHY the evidence was
gone in the first place. A 5MB main log, evicted by one dedup computation within ~20 seconds, is
not a retention window an audit trail can rely on — copying more rotated files only helps if the
event is still IN one of them, and under a sustained real workload it may not be.**

**Retention analysis (the actual numbers asked for):** the main log is `RotatingFileHandler
(maxBytes=5MB, backupCount=5)` — a 30MB total ceiling across 6 files. The dedup-flood burst
measured this session produced ~2.3MB of log volume in ~20s (~115KB/s sustained) — at that rate, a
single active file fills and rotates in **~43 seconds**, and the entire 6-file, 30MB budget is
consumed in **roughly 4-5 minutes** of sustained equivalent load. In practice it's worse than that
average suggests: the observed real burst (one `candidates/warm` call) filled and rotated the
ENTIRE active file on its own, meaning a single ordinary user action can already evict everything
older than about 20 seconds. That is not "long enough for a rare audit event to survive until
someone goes looking" by any reasonable standard.

**Decision: yes, implement a dedicated audit log.** `api.scan_initiated` (AN4, the specific event
this document has twice been unable to root-cause because of this exact gap) now also logs
through `logging_config.get_audit_logger()` — a second, independent `RotatingFileHandler` attached
to a dedicated `"reclaim.audit"` stdlib logger, writing to `reclaim_audit.log` (a sibling of
whatever the main log resolves to, so it automatically follows any `--log-path` override, e.g. the
frozen suite's own AZ4 isolation, with no new CLI flag needed). Propagation stays on by default —
audit events still reach the main log/console too; this is a pure addition, not a redirection.
Sized `maxBytes=1MB, backupCount=10` (10MB total): audit lines are one JSON object each, roughly
150-250 bytes, so this budget holds on the order of tens of thousands of real scan-initiation
events — orders of magnitude beyond any realistic personal-tool usage, and structurally immune to
being crowded out by an unrelated dedup/scan debug burst, because it is a completely separate file
with its own, independent rotation budget.

**Teeth-proof** (`tests/test_logging_config.py`, 4 new tests, all passing): a dedicated file
separate from the main log; propagation to the main log still works; reconfiguring for a different
path (test isolation) reconfigures the audit handler too; and the actual regression proof —
flood the main log with ~6MB of synthetic noise (enough to force a real rotation, asserted via
`reclaim.log.1` existing) and confirm an audit event logged BEFORE the flood is still readable
afterward. `scripts/verify.py`: 1217 passed (+4 from this PR), 94.52% coverage,
`logging_config.py` at 100%, all safety-gate floors met.

**Scope**: only `api.scan_initiated`'s three call sites were moved, matching exactly what was
asked ("scan-initiation logging") — not a general audit-everything pass. Other rare
security-relevant events (e.g. the scan-confirmation-token consumption/denial events) were not
evaluated for the same treatment this pass; worth a follow-up sweep, not done here.

now-orphaned file handle — a well-documented Windows behavior, not a contradiction. This explains
why AZ4's exit-code-5 guard (added specifically to catch a locked-file install failure) never
fired here: the install genuinely succeeded at the filesystem level; the survivor simply kept

## BL1 — reclaim_audit.log copied at "0 MB": a display bug, not a broken sink — investigated and disproven

## BL4 — Step 1's 3s/5-sample process polling replaced with a 100ms poll, after the requested event-log mechanism was confirmed infeasible

BH6's fix (baseline-PID-diff sampling) worked exactly as designed on a real trip and honestly
reported "no new PID observed" across 5 samples at 3s intervals — an accurate, non-misleading
result, but one that cannot distinguish "the task never spawned a process" from "the task spawned a
process too short-lived for 3s granularity to catch." The requested replacement — the Task
Scheduler Operational event log (Event IDs 129 process-created / 201 action-completed) — was
investigated and found **genuinely infeasible, verified directly, not assumed**:

- `Get-WinEvent -ListLog 'Microsoft-Windows-TaskScheduler/Operational'` → `IsEnabled: False`
  (disabled by default on this machine, and almost certainly on any real user's machine too).
- `wevtutil sl Microsoft-Windows-TaskScheduler/Operational /e:true` → failed with **"Access is
  denied"** unelevated. Enabling it would require UAC — directly against this project's own
  `reclaim.elevation.assert_not_elevated` invariant and the standing rule to never route around a
  UAC requirement rather than surfacing it.

Tried one further unelevated alternative before settling: a WMI `__InstanceCreationEvent`
subscription (`ManagementEventWatcher` on `Win32_Process`) — timed out against a real trigger, no
more reliable than polling against a process this short-lived.

**Measured the actual constraint instead of continuing to guess**: a real `reclaim.exe
check-disk-space` invocation completes in **~0.51s** wall-clock — the old 3s interval could
structurally never land a sample inside that window more than roughly half the time by chance, and
often not even then. Based on that measurement, tested a 50ms polling interval against 5 separate
real `Start-ScheduledTask` triggers — **5/5 caught the new PID, every time, on the first sample.**

**Fixed**: Step 1 now polls every 100ms (widened slightly from the validated 50ms for headroom
without hammering `Get-Process`) for up to 5s, breaking immediately on the first genuinely new PID
rather than running a fixed number of coarse samples — still ~5x the sampling density needed to
reliably land inside the measured 0.51s runtime. A catch now logs `[PASS -- BL4]`; a genuine miss
(no longer expected, given the live 5/5 validation) still logs the existing `[WARNING -- BH6]`, now
explicitly worded as newly surprising rather than routine, since this session's own testing found it
reliable. `LastRunTime`/`LastTaskResult` remain the primary, always-available, no-elevation-needed
evidence from Task Scheduler's own service regardless of this secondary check's outcome.

**Substitution reported, not silently made**: the user's specific request (Event IDs 129/201) is
not implemented, for the verified reasons above — the tight-polling replacement is the closest
achievable equivalent without requiring elevation.
